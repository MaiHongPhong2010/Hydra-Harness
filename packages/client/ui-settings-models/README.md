# @hydraharness/harness-client-ui-settings-models

Models settings and product-onboarding plugin. The same client Cordis plugin registers the Models page, a versioned internal-testing notice, and conditional navigation to provider configuration through `settings.onboarding`. The Models plane joins four wire domains into one shared snapshot — `llm.providers` (the configurable-provider directory with each route's live/dormant state), `settings.describe` (serialized schemas, layered redacted values, secret slots), `credentials.describe` (value-free configured/source/writable badges), and `authorization.list` (account identities without tokens) — and renders provider rows with one editor card at a time, without presenting route liveness as provider status.

Rows are the *configured* providers (their profile resolves in the owning namespace). Editors open only through an explicit Edit or Add action, including when every credential is missing. The add flow is a card carrying the dormant-directory provider select — a bare-mounted `llm-pi-ai` offers its whole installed catalog before any route exists. Optional non-chat providers use the `settings.models.provider-option` slot: each contribution owns its option, configured row, and editor card, while the Models page retains selection and close ownership. The page supplies value-free credential states for whole-section provider references and refreshes them on credential changes. Jev uses this slot so its general decision-provider credential never enters the LLM provider directory or conversation picker. The pi-ai card additionally edits that route's **model list** and can ask the provider what it serves. A row labels API-key state with a green solid dot only when a referenced credential is confirmed configured, and with a red solid dot only when a named reference is confirmed missing; reference-free provider-native authentication and unavailable credential enrichment remain unmarked. The editor is a hand-written card per adapter family: the primary **API key** input is followed by ordered fallback key inputs — the page never asks for an environment-variable name; a typed key stores **write-only** through `credentials.set` under the profile's reference, deriving `<ROUTE>_API_KEY` when the profile has none, and the pi-ai profile records that derivation as `apiKeyEnv`, so `settings.yaml` never carries a key value. Leaving all keys blank on a new pi-ai provider saves a reference-free profile and therefore preserves provider-native authentication such as the Bedrock credential chain or Vertex ADC. A successful Apply emits a local accessible status message without echoing secret material. The collapsed Customized settings fold carries the curated extras — `baseURL` and an optional HTTP(S) `proxy` for both families (the deepseek placeholder shows the public endpoint), each adapter's model catalog, and the **display name** and **API protocol** of a pi-ai route the adapter does not ship. A proxy scopes normal requests and **Fetch** to that route without changing another provider. Those two are what a hand-declared route names for itself: the create card asks for both because nothing can default them, so the editor reaches both rather than leaving them to `settings.yaml`. Clearing the name unsets it and the route falls back to its id, which is what the placeholder shows; the protocol has no such fallback. A catalog route gets neither — it defaults its name from its catalog entry, and its models each carry their own protocol, so a route-level one could only override every one of them. The Provider ID stays fixed: it is the settings key, the name every other namespace and every logged session references, and the stem of a credential reference the page cannot read back to move. Reasoning effort is deliberately NOT among them: it is a per-model capability and the models under one provider disagree about which levels they accept, so a provider-scoped control could only be set to a value some of them reject — which would hide even the models that support the level. The composer's model picker offers each model its own levels, and a switch there records provider, model, and effort together as the default for the next session. The profile field stays in `settings.yaml` for a deployment that knows its route. Each DeepSeek row edits `id`, optional display `name`, generation roles, and optional `contextWindow`/`maxTokens`; existing fields outside that curated set survive edits, while every other profile field stays owned by `settings.yaml`. A nested pi-ai profile is deletable when the user layer alone carries it (removal restores the composition base). The shipped official DeepSeek route is also deletable: confirmation records `ui-onboarding.deepseekOfficialDeclined` instead of unsetting the `llm-deepseek` composition section, so the adapter stays mounted while the row, selectable model catalog, and first-run prompt stay gone until the user adds that route again. Its localized confirmation dialog names the provider in the title, description, and final action. A row is tagged **Custom** when the directory entry says the owning adapter ships nothing under that key. The tag follows that answer alone: having a stored profile does not make a route custom — narrowing a shipped provider's models stores one too — and an adapter that reports nothing leaves its rows untagged rather than being read as shipped.

**Add API key** appends a masked fallback field. Save writes ordered `apiKeyFallbackEnvs` references into the profile and separately acknowledges each credential write. Blank existing fields preserve keys; successful writes clear their drafts, so a later failure retries only outstanding values. Removing a fallback unlinks it and deletes its credential only when its UUID reference belongs to this page and it is writable. Provider deletion uses the same rule. A configured fallback makes an active provider usable even when its primary key is missing.

The notice step owns its exact copy and version in `src/onboarding-copy.ts`. On loopback it compares and writes `ui-onboarding.welcomeNoticeVersion` through the existing settings API; only an explicit Continue records the current version. The Web composition base starts with `deepseekOfficialDeclined` set to `true`, and the Models page writes `false` when the user explicitly adds the shipped official DeepSeek row or `true` when the user deletes it. A non-loopback browser cannot use that Host-only namespace, so acknowledgement is process-local and the notice returns after reload.

After the notice completes, the provider step reads the shared Models snapshot. Any usable route skips setup: an active route with its named credential stored, or a reference-free route using provider-native authentication. When none is usable and writable provider configuration is available, the step opens **Settings → Models** and completes the current coordinator pass. It selects no provider, renders no separate API-key prompt, and writes no settings or credentials. The ordinary Settings close button and Escape dismiss the panel. Failed joins, failed credential reads, read-only settings, or an absent configurable directory leave navigation to the user. Official DeepSeek dismissal keeps that row hidden without preventing the user from configuring another provider. See the [provider-choice decision](../../../.agents/notes/implemented/bug-fix/2026-09-07-provider-choice-onboarding.md).

Every edit lands as `settings.mutate` path ops against the stored section — a set per changed field, an unset per cleared one, and a single unset for a deleted provider row. The page only ever holds the REDACTED descriptor, so it mutates the fields it can see rather than rebuilding a section. DeepSeek's `models` is one replace-by-value array: the editor shows inherited effective rows until the first model edit materializes the complete array in the user layer, while reset unsets that override. All provider catalogs show Model ID, Model name, Image, and Video columns, with role checkboxes directly on each row; context window and output cap sit behind the row's own disclosure, with the same fields the pi-ai provider form uses. Either capacity is typed as a count with an optional decimal `K` or `M` suffix (`256K`, `1M`; `1M` is 1000K) and stored as the plain count, spelled back in the shortest form that round-trips. Empty ids, duplicate ids, empty explicit names, and unreadable, non-positive, or fractional capacities fail before any write. A typed API key is judged on its own field the same way: after trimming, it must be non-empty and every character must be printable ASCII (`[\x21-\x7E]`), which is exactly what an HTTP header value can carry — the twin of `normalizeApiKey` in `@hydraharness/harness-llm`, mirrored here because the source-plane split forbids importing it. A value matching a pasted `NAME=value` environment line or wrapped in matching quotes is refused as the same format failure; that pasted-line check runs only in the browser, since a false positive in a resolver would leave the environment refusing the key as well. A field holding only whitespace fails rather than being silently dropped, while an empty field is not a failure at all: it means keep the stored key on an editor card, and authenticate some other way on a create card. A refused key blocks both the write and the endpoint interrogation, so the page never spends a round trip to be told what the field already says. Each settings write carries the card's current `revision`, so a concurrent write from another tab or an external `settings.yaml` edit is refused as `settings-conflict`; after settings commit, the card adopts the returned redacted user subtree and revision before storing the credential, which makes a failed credential stage retry only that stage. Deletion removes a configured, writable credential only when the profile names the page's derived `<ROUTE>_API_KEY` target, then unsets the profile — except official DeepSeek, which unsets that managed credential the same way and then records `deepseekOfficialDeclined` rather than unsetting the whole `llm-deepseek` section; both operations are idempotent, and a partial failure remains in the identified confirmation dialog for retry. Environment credentials, custom references, and credentials whose target cannot be identified remain untouched. Once loaded, the page subscribes directly to forwarded `settings/document-updated`, `credentials/reference-updated`, and `llm/adapters-updated` owner events, plus local `connection/reset`, so an external `settings.yaml` edit, a second tab, or a settings-born route converges without polling.

## Model list and endpoint interrogation

Applying an explicit pi-ai model list clears shared Image/Video model choices targeting removed or renamed IDs on that provider in the same revision-checked settings write. Choices whose IDs remain, including those on other providers, are retained. Cancel saves neither the catalog edit nor preference changes.

In discovery editors, catalog actions share one row beneath the Models heading: **Restore** uses an amber button, **Get all** uses the primary fill, and **Fetch** uses a neutral outline. Hover explanations distinguish restoring defaults, adopting all available models, and choosing models to add; model changes are saved with **Apply**. Unavailable discovery actions explain the missing endpoint or invalid key. Narrow panels retain equal button heights.

Clearing an endpoint or proxy override makes discovery use the composition value or schema default; an absent inherited value stays absent in the request. A provider created by the current card does not count as a duplicate during a credential-only retry, even after the directory refresh lists it.

A pi-ai profile's `models` list is edited on the card: one row per model showing its id and display name, with the context window and output cap behind a per-row disclosure and two label-free actions — expand and delete — on the right. An empty list means "serve this route's built-in catalog", so a row is only ever added deliberately; clearing a capacity drops it rather than storing a value the schema would reject, and the adapter's route-level fallbacks size whatever configuration leaves out — an empty capacity shows those fallbacks' magnitude as its placeholder, a hint rather than a mirror, since the field counts `K` as 1000 and a deployment may override them. A capacity that is not a positive integer is simply not stored.

**Fetch** asks `llm.discoverModels` about the endpoint the form **currently shows**, including a base URL edited but not yet saved and a key typed but not yet stored, so adding a provider is one pass instead of save-then-return. The reply opens a wider picker with **Model ID**, editable **Model name**, and **Image**/**Video** checkbox columns. Endpoint metadata prefills generation roles; either or both can be selected, while leaving both unchecked keeps ordinary models. Changing a role saves explicit endpoint metadata, including a conversation marker when both are cleared, so model-name inference cannot undo that choice. Saved rows use the adapter's shared family inference when explicit endpoint metadata is absent; an explicit conversation marker wins. Saved rows expose the same role checkboxes in API-key, custom, and account provider editors, including direct DeepSeek. Checkboxes use the theme accent and retain native keyboard selection and visible focus. Provider names are prefilled; missing names leave the value and placeholder empty, and cleared names are omitted on adoption. **Add selected** copies the chosen entries and names into the provider draft; **Apply** persists that draft. Candidates already configured start unchecked, and adoption preserves their existing metadata except a classification explicitly changed in the picker. **Select all** / **Deselect all** changes only the adoption checkboxes and retains classification; nothing is written until **Add selected**. A provider that cannot be interrogated is a detour, not a dead end — the adapter's own message appears beside the rows, which stay editable by hand.

**Add a custom provider** declares a route pi-ai does not ship. It is its own card rather than the editor with extra fields, because the route id is being chosen here and the settings address does not exist until it is: one `settings.mutate` sets the whole profile at `providers.<route>`, and the key travels separately through `credentials.set` under the same `<ROUTE>_API_KEY` derivation an existing provider uses. What a hand-declared route cannot default gates the create button — a unique **Provider ID**, an endpoint, a protocol, and at least one uniquely-identified model — so the failure names the field while the user is still looking at it. The id must start with a lowercase letter, because it is also the stem of the derived credential reference and a reference is a POSIX shell identifier: a digit-leading id otherwise passes every check this card makes and then fails at the credential seam with a raw regular expression. Capacities do not gate it: the adapter's fallbacks size a model the endpoint described by id alone, which is what most listings return. The protocol choices are read out of the namespace's own schema rather than a wire field or a constant, so they cannot drift from the ones the adapter accepts. The card records the conventional `apiKeyEnv` reference only when a key is typed, the same rule the editor applies, so a route declared for provider-native authentication is not born pointing at a reference nothing will ever set. When the profile write lands but the key write fails, the provider already exists: the card settles the fields describing it, retries the credential alone — re-running the profile write would carry the revision that write just superseded, so the Host would answer `settings-conflict` and the key could never be stored from here — and reports the created provider even if the user then cancels.

An empty **Max output tokens** field in the shared model editor shows **Unlimited** and saves no model cap; clearing a stored count removes it. Provider and model limits still apply, and APIs requiring an output cap use their adapter's resolved model capacity. Explicit model counts and request budgets remain supported ([pi-ai output settings](../../llm/llm-pi-ai/README.md)).

## Account sign-in

Use the **Account sign-in** section's **Add sign-in provider** action, then choose **ChatGPT**, **Google**, **Gemini Web**, **Claude**, **xAI**, **Kimi Code**, **Cursor**, or **Kiro**. Google connects Antigravity through Google OAuth without asking for a Cloud project ID. Apply enables Antigravity and preserves configured counterparts. Cursor manages accounts and its editable catalog, disables unsupported discovery, and displays its unavailable chat transport explicitly; callable routes enter the model selector after Apply. API-key fields remain in the separate **API keys** section. Ordinary sign-in links open in the Desktop system browser. Gemini Web instead provides **Connect**, **Reconnect**, and **Remove** for one account in a separate managed browser; its [account adapter](../../llm/llm-account-auth/README.md#gemini-web) owns platform, profile, HTTP validation, and media restrictions. Add shows login controls without an account list or quota requests; use the provider's **Edit** card to manage connected accounts. Closing the editor cancels only the login that editor started, including a start response arriving after it closed.

Connect **Gemini API** through **API keys → Add a custom provider → Provider template → Gemini API**. The template fills an editable `gemini` route ID, display name, native Gemini endpoint, and `google-generative-ai` protocol. Enter an API key and use **Fetch** or **Get all** to select models before creating the provider. API quota and billing are separate from a Google AI plan. Saved `llm-account-auth/gemini-api` OAuth configurations appear under API keys for editing and removal, retaining their project prompts and shared Antigravity account pool. They are excluded from new-provider selectors. The [onboarding decision](../../../.agents/notes/implemented/feature/2026-10-03-gemini-api-custom-provider.md) owns this separation.

**Delete** removes the selected provider's configuration and every account saved for it in Hydra, then closes the confirmation after Host acknowledgement. OAuth browser sign-ins are kept; Gemini Web also removes its separate Hydra browser profile while retaining saved media and recovery jobs. Deleting either Antigravity or Gemini API clears their shared Google account pool while retaining the other service's catalog; its confirmation identifies both services. Credential removal precedes configuration removal so a storage failure keeps the provider visible for retry. Use **Sign out** in Edit to remove only one OAuth account. The [account editor and removal decision](../../../.agents/notes/implemented/bug-fix/2026-10-03-provider-account-editor-and-removal.md) owns these actions.

Deleting a pi-ai provider also forgets its local SDK credential record, whether it contains an API key or an OAuth grant, before removing the page-managed primary and fallback API keys. Other provider records and API-key references are retained.

When Antigravity and Gemini API are both configured, the Google editor's **Fetch** and **Get all** query both and preserve their identities in one grouped picker. With a single configured service, these actions query only that service. Names and Image/Video flags are edited per service even when ids repeat. Both catalogs remain reviewable as drafts; **Apply** saves their changes together, and Cancel discards them. A failed service is identified while the other's results remain usable. The [shared discovery decision](../../../.agents/notes/implemented/feature/2026-10-03-shared-google-model-discovery.md) owns these selection and save semantics.

Account credentials are stored by the Host. The browser receives account names and transient login instructions; Gemini Web's **Import Cookies** additionally accepts a user-selected Google cookie JSON file or masked paste, sent only as a secret authorization answer and cleared after submission. The sign-in method selector offers managed-browser Connect and cookie import in Add and Edit; HTTP validation must finish before success. Failed imports keep the connected account. The [account-auth adapter](../../llm/llm-account-auth/README.md#gemini-web) owns accepted formats, size limits, account matching, initialization, refresh, and request behavior. OAuth pools rotate through accounts before visible output; Gemini Web uses one account without generation retries. An account-backed route with no connected accounts remains unavailable for onboarding readiness.

The provider's **Edit** card shows a searchable account list with ten rows per page and an Add account action above it. Search matches account labels and IDs across the whole pool. Multi-account pools start with usage collapsed; expanding one row fetches its quota, caches the result until refresh, successful login, or editor close, and cancels pending usage when the row leaves view. A sole account opens automatically. Starting sign-in temporarily hides the inventory while preserving search and selections. A newly added account clears search and opens on its page; reconnecting clears cached usage so the expanded row obtains a fresh report. Usage appears as small circular meters with remaining percentages and short labels beneath the account. Reset times, remaining counts, and full model names appear on hover or keyboard focus. Banked resets and credits use compact rows. Codex shows its five-hour and weekly windows and banked reset count; Google Antigravity groups provider-reported model buckets under Gemini, Claude/GPT, or other models, including reset times, remaining counts, disabled states, and credit balances when supplied. Missing provider fields stay unavailable instead of becoming inferred quotas.

**Select this page** selects only the displayed matches. Selections persist across pages and searches; **Remove selected** opens a confirmation listing every selected account. Removal writes through the Host one account at a time, refreshes the inventory once, and retains failed removals for retry. Acknowledged removals leave the list even if its final refresh fails. Closing the editor stops starting further removals after the current request returns. Browser sign-ins remain available. The [large-pool decision](../../../.agents/notes/implemented/feature/2026-10-03-scalable-provider-account-management.md) owns these behaviors.

The top of Models has exactly two shared dropdowns: **Image model** and **Video model**. Each shows models classified for its generation role across all providers and retains provider identity when model ids repeat. Ordinary models are excluded; a model marked for both appears in both selectors. An existing preference whose model loses its role remains visibly unavailable until the user clears or replaces it. In a provider editor, **Get all** reads its complete listing, follows Gemini pagination, and adds entries to the draft while preserving existing edits; **Apply** saves that catalog. The shared selectors then save top-level `imageModel`/`videoModel` provider/model pairs in `llm-pi-ai`. The composer's Model menu reads and writes those same preferences through the shared settings mirror. A selection takes priority over a tool's default model and declares generation use for unknown ids; actual generation still requires a supporting adapter and provider access. Fetched endpoint metadata survives edits to model ids, names, and capacities. Generation-only models remain available to tools and are omitted from the conversation selector.

The shared selectors refresh after any provider namespace changes, including account catalogs, while retaining unapplied image/video choices. The ChatGPT account editor identifies its Codex image catalog supplement and explains that image access is checked during generation. Its Fetch action combines the live conversation catalog with the account adapter's supported image entries; Codex video transport remains unavailable. The [account-auth adapter](../../llm/llm-account-auth/README.md) owns these model ids and native endpoints.

The Gemini Web editor links to the published cookie-copy guide before login starts. The Import Cookies prompt includes **How to copy cookies**, a native disclosure linking Cookie-Editor's official site and describing active-tab JSON export. The [user guide](../../../docs/user/guide/providers.md#import-gemini-web-cookies) owns the complete copy and import procedure.

## Known Limitations and Deferred Work

- **Only account actions, API keys, and curated fold fields are editable on the card** — the hand-written editor traded schema-generic field coverage for the mockup layout ([Agent Note](../../../.agents/notes/implemented/architecture/2026-07-30-web-config-plane.md)). Both families expose `baseURL`, `proxy`, and model `id`/`name`/`contextWindow`/`maxTokens`; a hand-declared pi-ai route also exposes `displayName` and `api`. Retry policy, timeouts, DeepSeek model descriptions, and other advanced fields remain in `settings.yaml`; existing model fields the editor does not show are preserved. A profile schema without the conventional fields renders the hint alone, and the curated layouts key on the `llm-deepseek`, `llm-pi-ai`, and `llm-account-auth` namespaces by name.
- **Credential cleanup is intentionally narrow** — deleting a row removes the configured, writable credential only when its reference is the exact `<ROUTE>_API_KEY` target this page derives. Custom references, environment credentials, and unidentifiable targets are retained because the row cannot prove ownership of them.
- **Only pi-ai routes can be hand-declared** — the custom-provider card writes into `llm-pi-ai`, the one namespace whose profiles describe a whole provider. The official `llm-deepseek` route remains a composition fact this page cannot create; dismissing it only hides the Models row until the user adds it again.
- **Interrogation covers OpenAI-compatible and Gemini endpoints** — other protocols report that they cannot be asked and retain hand-entry.
- **Undeclared live routes render nowhere** — a route registered without a configurable-provider declaration has no settings address; it stays visible in pickers but not on this page's rows.
